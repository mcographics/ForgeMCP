# ForgeMCP Phase E — Connection Bootstrap Redesign Plan

Date: 2026-10-22 (America/Toronto)  
Scope: source/configuration review and design only  
Disposition: **No implementation or connection attempt performed.** This plan separates a confirmed startup-observability defect from unproven causes of the historical Codex handshake failures.

## Findings

The historical actual-client record shows failed MCP startup waits, but it does not establish which internal MCP handshake step failed. The recorded client wait windows were approximately 30 seconds at 22:10:28.726–22:10:58.726 EDT and 20 seconds at 22:10:42.818–22:11:02.818 EDT. They overlap as client-side waits; the evidence does not prove that two live Python children overlapped for those full intervals. The effective project entry recorded in the prior investigation used the venv interpreter, `-m server.main`, `G:\ForgeMCP` as cwd, `FORGE_PROJECT_ROOT`, and the corrected session-directory environment. `FORGE_HOST_MODE` was absent from that saved entry, so the process's inherited value is unknown. One empty PID log file was created during the final window, but cannot be assigned to either attempt. The 20/30-second difference is real; its source is **unknown** and is not attributed here to a particular setting.

The October 22 bounded SDK-client run is useful comparison evidence, not actual Codex-client acceptance. It used the venv interpreter, the same module and cwd, `-B`, `FORGE_PROJECT_ROOT`, and the installed MCP SDK stdio client; it completed initialization, tool discovery, authenticated requests, and exited normally. That test's complete inherited environment was not captured. Its runner, process orchestration, `-B` argument, and environment may differ from Codex. No one difference is proven causal.

| Classification | Finding |
|---|---|
| **Confirmed defect: startup diagnostics** | `FastMCP(...)` is constructed at module import, and its installed SDK constructor calls `configure_logging()`. In MCP SDK **1.30.0**, that function calls `logging.basicConfig()` with a stderr handler. `server.main.main()` later constructs a PID-specific `RotatingFileHandler` and calls `basicConfig()` again. Python's default `basicConfig()` does nothing once the root logger has handlers, so the later file handler is not attached. Its constructor can create an empty file, matching the historical empty log. This explains missing diagnostics, not the handshake failure. |
| **Confirmed code path: production bootstrap** | `ConnectionManager.configured()` defaults to production mode and reads configuration/environment without discovering or authenticating an Unreal session. Tool decorators construct the registry during import. Production engine discovery and authenticated health probes are performed by the lifespan-owned monitor after stdio startup begins. This source path does not support the claim that production session discovery necessarily blocks MCP initialization. |
| **Confirmed code path: isolated bootstrap** | The isolated lifespan starts its identity worker and awaits authenticated `health` and `project_info` plus project validation before yielding. The installed low-level MCP server enters lifespan before it consumes protocol messages. Thus isolated mode intentionally puts worker and engine preflight on the initialize path. Whether a failed Codex launch used this branch is **unknown** because its effective `FORGE_HOST_MODE` was not recorded. |
| **Plausible causes, unproven** | Slow imports; client/child scheduling; inherited environment differences; isolated-mode preflight; a first synchronous production registration scan; or another resource delay could affect readiness. There is no evidence that the connection manager caused the actual Codex timeout, that stdout was contaminated, or that the native bridge was contacted during those failed handshakes. |
| **Architectural improvement** | Make the process entry and import milestones observable, keep engine readiness out of the MCP protocol bootstrap where policy allows, and keep each background worker/task owned by that host's lifespan. This improves diagnosis and startup independence without replacing the MCP protocol or weakening request checks. |

## Current startup and protocol boundaries

The current flow is:

1. Python executes `python -m server.main`; package initialization is currently only a docstring.
2. `server.main` imports FastMCP, Pydantic, all tool modules, and the connection monitor, then constructs the `FastMCP` app and `ConnectionManager`.
3. The `@mcp.tool` decorators register the application tools during module import. In the last bounded SDK client result, the catalog contained **114 tools**, including all five Landscape tools; that count is historical, not freshly measured in this design pass.
4. `main()` applies the isolated tool allowlist if configured, prepares log directories, creates a file handler, and calls `mcp.run(transport="stdio")`.
5. The SDK's `FastMCP.run_stdio_async()` enters `stdio_server()`, which owns stdin and stdout framing. The low-level server then enters the configured lifespan **before** its incoming-message loop.
6. After lifespan yields, the low-level server receives protocol requests. In SDK 1.30.0 it logs `Processing request of type ...` before dispatch. The session handles `InitializeRequest` and writes the response through the SDK's responder and stdout writer.

The installed SDK's `stdio_server()` serializes protocol messages to stdout as JSON-RPC lines and flushes each line. FastMCP's logging setup targets stderr. A source scan found no import-time `print()` in the `server.main` import path. The listener helper's stdout is a separate child-process JSON protocol and is captured by its parent; it does not share the MCP host's stdout. A helper's `print()` is therefore not evidence of MCP stream contamination. No existing captured Codex trace contains raw ForgeMCP stdout or a malformed JSON-RPC response.

The startup stages should be reported with explicit observability limits:

| Milestone | Evidence to collect in a future bounded test | Limit |
|---|---|---|
| 1. Codex requested startup | Owning Codex log entry with timestamp, server name, and a per-attempt correlation ID if the client exposes one. | Existing records do not always correlate a launch line to an OS PID. |
| 2. OS created host process | OS process-creation event or a client-owned child PID correlated to the attempt. | A Python marker cannot prove when Windows created the process. Use only existing OS telemetry or a later authorized test harness; do not add a surrogate host. |
| 3. Python entry and imports completed | A minimal bootstrap's first structured stderr event and a second event after importing/registering the existing app; include PID, PPID, startup ID, monotonic timestamp, elapsed time, and sanitized cwd/executable. | The first Python statement occurs after interpreter and module-loader initialization. A missing marker still cannot distinguish OS creation from pre-entry interpreter startup. |
| 4. MCP stdio transport entered | Structured event at the start of the app lifespan. In this SDK, `stdio_server()` is opened immediately before low-level `Server.run()` enters lifespan. | It confirms local transport setup reached application lifespan, not that the client sent a request. |
| 5. Initialize request received | The installed low-level server logger records `Processing request of type InitializeRequest`. A small logging filter/handler can emit a structured event to stderr or the diagnostic file without reading message contents. | This observes receive/dispatch, not response success. It is tied to the installed SDK's log wording and must be regression-tested on upgrades. |
| 6. Initialize response emitted/accepted | Owning Codex client's successful MCP initialize result or an actual MCP SDK test client's `initialize()` completion. | The SDK server exposes no suitable public response-emitted callback. Do not wrap, read, or intercept stdio streams just to infer this. |
| 7. Tool discovery completed | Actual Codex client exposes the discovered tool catalog; offline protocol test's `ClientSession.list_tools()` result; record only count and schema/catalog hash if useful. | Server-side receipt of `ListToolsRequest` alone does not prove its result reached or was accepted by Codex. |

Diagnostic records should be JSON lines on stderr or a dedicated file, never stdout. Fields should be limited to `event`, a random startup ID, PID/PPID, monotonic nanoseconds, elapsed milliseconds, sanitized executable/cwd, host mode, and safe counts/status codes. Do not log registration contents, tokens, native request bodies, project credentials, or exception strings that may contain payload data. Catch and categorize expected startup failures; send tracebacks only to stderr/file with explicit redaction review. Use an explicit logger/handler rather than relying on a second `logging.basicConfig()` call.

## Proposed bootstrap architecture

Keep the existing Python executable, venv, stdio transport, project cwd, environment contract, FastMCP app, tool declarations, schemas, names, and handlers. Add a tiny `server.bootstrap` module and change only the existing module argument from `-m server.main` to `-m server.bootstrap` when the actual Codex test is authorized. The bootstrap emits its first safe marker, imports `server.main` (which constructs the one existing FastMCP server and registers its tools), emits import/registry completion, then invokes the existing `main()` function. It must not construct a second FastMCP server, parse/forward protocol messages, or implement another transport.

The installed SDK's stdio implementation remains the sole protocol owner. Tool registration must complete without contacting Unreal. The production `ConnectionManager.configured()` path already has this property and should be preserved. Engine discovery/authentication stays in the existing lifespan monitor and individual request handlers. A missing or unavailable Editor must produce the existing bounded `BridgeError`/typed tool result on the affected operation; it must not prevent a standards-compliant initialize or tools/list response. Every native request continues to use its existing session allowlist, private registration, token authentication, and applicable fresh process identity checks. Do not cache positive identity or grant access from discovery alone.

For isolated mode, the catalog remains restricted to its current allowlist, and authorized operations remain fail-closed. The current isolated lifespan preflights the native bridge before yielding; separating that preflight from MCP initialization is a candidate change only if actual configuration evidence shows this branch is in scope. A later design may serve the same restricted catalog immediately while reporting engine unavailable to each tool, with existing identity/authentication checks still required before any operation. This must be validated against current isolated-mode safety expectations before adoption; no bypass is proposed.

The host owns its monitor task and any identity worker in its lifespan. Cleanup must be in a `try/finally` that also covers worker startup and all awaits. Cancellation of `asyncio.to_thread()` does not stop the worker thread, and shielded identity work can outlive the awaiting coroutine; worker shutdown must not race an outstanding query. Tests should prove ownership and bounded cleanup rather than assume coroutine cancellation kills native work. Do not add a process-global/singleton lock: separate legitimate MCP clients remain independent processes with independent server lifespans and owned workers.

## Reuse and lifecycle assessment

| Component | Reuse decision | Reason / guard |
|---|---|---|
| Five foundation inspection tools and existing FastMCP registry | Reuse unchanged. | The task is startup reliability, not tool semantics. Snapshot the full public catalog and schemas before any future refactor. |
| `ConnectionManager.configured()`, registration parsing, allowlists, token authentication, response validation, and identity probe | Reuse unchanged. | No evidence identifies a defect in these security boundaries. Maintain per-request authentication/fresh identity behavior and current timeouts. |
| Installed MCP SDK `stdio_server()` and FastMCP stdio run | Reuse as-is. | SDK owns framing and writes protocol JSON only to stdout. No custom protocol layer. |
| Production periodic monitor | Reuse initially. | It is started under FastMCP lifespan and sleeps between authenticated health cycles. Keep its existing cadence and behavior; measure actual idle indicator behavior later without extra requests. |
| Isolated persistent identity worker | Reuse, do not confuse with an MCP daemon. | It supplies TCP-table ownership queries in isolated identity checks. It is not a Codex host and does not create a persistent Codex connection. |
| Global process-level coordination | Do not introduce. | Existing managers are host-process scoped; a global lock would make independent clients interfere and is not justified by evidence. |

Lifecycle risks to cover are: isolated worker startup currently occurs before the lifespan cleanup `try/finally`; cancellation while `asyncio.to_thread(worker.start)` is running may leave a later-started worker without cleanup. Also, identity work already running in a thread may outlive coroutine cancellation while the lifespan is closing the worker. These are code-structure risks in the isolated branch, not a demonstrated cause of the historical production Codex failure. Production monitor cancellation already cancels and awaits its task. A synchronous production registration directory scan occurs at the start of each monitor iteration; it is filesystem-only and has no explicit duration bound, so measure it, but there is no evidence it caused the reported handshake waits.

## Risks and first safe step

The bootstrap marker cannot observe OS process creation or Python interpreter initialization before its first Python statement. The installed SDK request log is useful but version-coupled; an SDK upgrade should fail a diagnostic regression test rather than silently lose receive milestones. Adding diagnostics before the current `FastMCP` construction is necessary to record import/constructor time, and the current PID file handler must be attached explicitly. A future B change risks making a limited isolated catalog visible before native preflight; that is acceptable only if every operation still checks its exact allowlist, registration, identity, and authentication and the exposed catalog is intentionally unchanged.

**First safely reversible implementation step after review:** Increment A only—add `server.bootstrap` with stderr-only structured markers and a small test proving it reaches registry construction and enters the existing stdio server without stdout diagnostics. Fix the existing file-handler wiring in the same diagnostics-only increment. Do not alter the monitor, connection manager, timeouts, tool behavior, native plugin, authorization policy, or Editor. Once the offline diagnostic path passes, the owner can review the single MCP-entry argument change needed for Increment E. This task does not make that change.
