## Patch audit: source and API behavior

The review artifact is [ForgeMCP_0.2.17_TedsOutliner_StartupFix_Proposed.diff](ForgeMCP_0.2.17_TedsOutliner_StartupFix_Proposed.diff). `git apply --check` against the installed UE 5.6.1 tree passed read-only; **this is not a C++ compile or runtime test**. The original files under `Engine/Plugins/Experimental/EditorDataStorageFeatures/Source/TedsOutliner/{Public,Private}` were read but not modified.

The existing `FTedsOutlinerModule::StartupModule()` calls `RegisterLevelEditorTedsOutlinerTab()`, whose first action is `GetModuleChecked<FLevelEditorModule>("LevelEditor")`. The failed crash stack names `UnrealEditor-TedsOutliner` immediately after Core at the unloaded-LevelEditor assertion. The precise function address remains unsymbolized. The patch subscribes to `FModuleManager::OnModulesChanged`, registers immediately when LevelEditor is already loaded, or defers until its `ModuleLoaded` event. Installed `ModuleManager.cpp` sets the loaded module's `bIsReady=true` **before** broadcasting `ModuleLoaded` at lines 903 and 1033. `GetModulePtr` returns null when no module object exists. This supports the callback's timing and pointer guard.

The patch adds duplicate delegate protection, checks for a valid LevelEditor tab manager, checks `HasTabSpawner`, and removes its module-change callback at shutdown. Installed `LevelEditor.cpp` creates a new tab manager and then broadcasts `TabManagerChanged`, while replacing an old manager calls `UnregisterAllTabSpawners`; the proposed callback can register on both the current manager and a new one. `FTabManager::HasTabSpawner` and `UnregisterTabSpawner`, `FLevelEditorModule::OnTabManagerChanged`, and `FDelegateHandle::Reset` exist in installed headers. `ModuleUnloaded` notifications are broadcast for ordinary unloads **after** the module is unloaded; they are intentionally suppressed during global shutdown. The patch clears retained state on an ordinary LevelEditor unload and uses `GetModulePtr` at TedsOutliner shutdown rather than dereferencing an unloaded module.

**Audit risks before compilation:** the patch has not been type-checked against a real target. It adds a public-header include of `ModuleManager.h`, and the exact callback/delegate instantiation must compile. The `ModuleUnloaded` path clears the handle after LevelEditor has already gone; this is consistent with the module-manager sequence but needs lifecycle testing to rule out residual delegates or stale tab spawners. A same-name spawner installed by a different owner would make `HasTabSpawner` skip TedsOutliner's registration, so ownership assumptions need review. Other existing TedsOutliner `GetModuleChecked<LevelEditor>` calls remain in user-triggered paths; the patch addresses the probable startup path, not every possible unload race. Repeated module unload/reload may be unsupported in some installed-build contexts; test it only where the Engine permits it. No compilation success or runtime correction is claimed.

## Installed build and binary facts

`Engine/Build/InstalledBuild.txt`, `Engine/Build/BatchFiles/Build.bat`, `RunUAT.bat`, and `Engine/Binaries/DotNET/UnrealBuildTool/UnrealBuildTool.dll` exist. `BuildPluginCommand.Automation.cs` documents `-Plugin`, `-Package`, and optional `-EngineDir`; it constructs a host project, calls UBT for `UnrealEditor` Development on host platforms, and packages build products. Its package output must be outside the Engine directory; it may clear an existing package-output directory. This establishes a supported **plugin packaging mechanism**, not that a changed copy of this particular installed Engine plugin can replace the module used by an isolated Editor. No BuildPlugin or Build.bat command was run, including a dry run.

The installed BuildPlugin implementation has an additional **source-write side effect**: when a plugin lacks `Config/FilterPlugin.ini`, it creates that file in the supplied source plugin directory before constructing its host project (`BuildPluginCommand.Automation.cs` lines 97–111). The installed `EditorDataStorageFeatures` plugin currently lacks this file. Therefore even a package output path outside the Engine would **not** make a BuildPlugin invocation against the installed plugin safe. The command can also clear an existing package-output directory (lines 87–90) and creates/copies a host project. Any future approved invocation must use disposable plugin source and a newly empty disposable package destination, with its write paths verified beforehand. No such invocation was made here.

MSVC 2022 Community with `cl.exe` versions 14.38.33130 and 14.44.35207 was found; Windows SDK libraries 10.0.22621.0 and 10.0.26100.0 are present. The installed Editor reports UE 5.6.1, compatible changelist 43139311. Existing `EditorDataStorageFeatures/Binaries/Win64/UnrealEditor.modules` has BuildId **43139311** and maps TedsOutliner to `UnrealEditor-TedsOutliner.dll`, matching the installed Editor module manifest BuildId. The existing DLL and PDB are present. Their presence does not establish that a future output would match ABI, exports, import libraries, BuildId, or manifest registration. A future build would need independent verification of all of those before launch.

## Isolation options

**A. Independent physical Engine copy:** This is the preferred architecture *if* a copied installed build can build and load the patched Engine plugin. Patch/build only inside that copy, use a physically separate project clone and private DDC, then verify the copied Editor actually loads the copied `TedsOutliner` DLL with a compatible manifest. The installed Engine would remain untouched. The supported copy-local UBT/build procedure, generated paths, module metadata, and write footprint have not been demonstrated. Therefore this is an architecture for further investigation, not an approved build recipe.

**B. BuildPlugin package:** The installed automation supports compiling/package output outside the Engine. It creates a host project and output products, which may include `.dll`, `.pdb`, and `.modules` for Editor modules. A package by itself does not determine which `EditorDataStorageFeatures` instance Fab will load when the installed Engine already contains that plugin. Placing a second same-name plugin in a project has unverified discovery/selection behavior and is rejected as a deployment shortcut. Copying packaged binaries over the installed Engine is prohibited. Packaging may eventually be a compilation step for an independent Engine copy, but the runtime route is not yet proven.

**C. Other override mechanisms:** No verified project-local per-module replacement or module-specific plugin override was found in the inspected descriptors/tooling. Renaming the plugin/module would alter Fab's dependency chain; disabling Fab or EditorDataStorageFeatures is out of scope. Symlinks, junctions, hardlinks, and shared writable Engine binaries fail the isolation requirement.

Rollback for any future approved isolated build must be confined to discarding **disposable** Engine/project copies and generated artifacts after evidence retention; no production or historical checkpoint restoration is involved. This report authorizes neither creation nor cleanup of such copies.

## Fab, ForgeMCP, and Stage 2E compatibility

The project explicitly enables Fab; installed `Fab.uplugin` explicitly enables EditorDataStorageFeatures, and Fab source uses Editor Data Storage features. The proposed patch does not disable any module or change the plugin descriptor, preserving the static enablement chain. It also leaves LevelEditor, Landscape, World Partition, and ForgeMCP source and binary dependencies unchanged. Actual Fab behavior and ForgeMCP session/height readback after loading a changed TedsOutliner binary cannot be inferred from static dependencies. A future isolated run must verify them separately.
