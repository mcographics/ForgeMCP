## Implemented source scope

The new API leaves the legacy recipe system and its existing interfaces intact. It adds a separate typed adapter for one existing, unambiguous ordinary K2 graph in a normal, compiled Blueprint:

| Operation | Identifiers and validation |
| --- | --- |
| `move_node` | Exact unique NodeGuid; supported native node adapter; bounded integer x/y; no-op and duplicate position edits rejected. |
| `set_pin_default` | Exact node GUID and PinId; unlinked, non-orphaned primitive input; native K2 parsing and validation; bounded complete value; object, text, reference and container defaults excluded. |
| `disconnect_pins` | Exact source/destination node and pin IDs; existing reciprocal link; output/input directions verified. |
| `connect_pins` | Exact typed endpoints; native schema compatibility; no wildcard/promotion/conversion node creation; required existing execution/data links must be explicitly disconnected earlier in the sequence. |

The first adapter accepts known fixed native K2 node profiles. Unknown node classes, custom schema/graph classes, structural operations, implicit link replacement, dirty packages, missing original disk packages, and unsupported platforms are rejected explicitly. Native function/member identities and resolved parameter signatures are part of relevant preconditions; a friendly node title is never an identifier.

The request allows 1–32 operations. It uses strict Pydantic models with unknown fields forbidden, exact package/node/pin selectors, and bounded values. Native validation repeats the checks for authenticated bridge clients. Native preview IDs are normalized to lowercase hexadecimal to match the MCP Apply schema.

### MCP interfaces

- `unreal_preview_blueprint_graph_patch(request, session_id)` dispatches `blueprint_patch_preview`.
- `unreal_apply_blueprint_graph_patch(preview_id, confirmation, session_id)` dispatches `blueprint_patch_apply`.

Apply requires authorization for the exact reviewed asset and change set; `confirmation == preview_id` is replay/review binding, not independent proof of human consent. Native plans are process-local, expire after 600 seconds, have a 32-plan limit, and are consumed once. They bind the Blueprint/graph/node objects, exact graph path, project and world context, relevant before-values, pin/member types, links, dirty state, compiled baseline, and original disk file hashes.

## Scoped journal and separate package backup

`ForgeBlueprintPatches.cpp` does not call the legacy whole-Blueprint `Snapshot`. Each plan records targeted positions, pin defaults/types, exact links, and prefix revision digests for the proposed operation sequence. The target before/after records have an explicit 128 KiB UTF-8 budget. This limit applies to the actual edit scope, not the total node count or unrelated graphs.

The package must already exist on disk and be clean. Preview inventories the package header and existing UE 5.6 package sidecars using the native `EPackageExtension` names: exports, default/optional/memory-mapped bulk data, and payload sidecar. Every selected file must be in this project's Content directory and use a non-reparse path.

Before mutation, Apply revalidates the disk file set and hashes, copies those files with their project-relative paths into a new private journal directory, and rehashes source and destination. It refuses to overwrite a previous backup directory. The backup is stored separately from `journal.json` under:

`Saved/MajesticForge/BlueprintJournals/<preview_id>/OriginalPackage/Content/...`

Streaming Windows CNG SHA-256 reads files in 64 KiB chunks. The new path does not load a whole package file into memory merely to hash it, and it does not invoke an unimplemented generic-platform SHA routine. Other platforms currently return `unsupported_platform` for this adapter. Local file backup verification does not constitute an isolated recovery rehearsal, a backup of external referenced assets/virtualization services, or proof that a modified Blueprint survives an independent reload.

The prepared journal is written before the Editor transaction starts. Failure to inventory, copy, verify, or write that journal prevents graph mutation. A partial backup directory can remain as diagnostic evidence; it is not automatically deleted, reused, or restored over project content.

## Apply, compile, preservation and rollback

Apply uses an Editor transaction, native schema default/link APIs, and native Blueprint compilation with saving skipped. It verifies each operation against the expected prefix digest. It never silently breaks an existing execution path to make a new link.

Before and after Apply, streaming semantic SHA-256 checks cover every graph's node identities, native member/function references, positions/comments, pin identities/types/defaults, and connection topology. Only the exact planned fields are excluded from the untouched comparison. A separate digest covers variable declarations, reflected editable/Blueprint-visible CDO defaults, and own SCS component declarations and editable template defaults. This is additional protection rather than full inherited-component or arbitrary special-node support.

The journal is scoped; the verification still scans graphs/defaults and backs up the complete selected local package files. Its runtime cost is therefore not independent of asset size. Performance is unmeasured. There is no total graph-node snapshot bound or `asset_too_large` check inherited from the legacy editor on this new path.

If an operation or compilation fails, restoration is attempted only when the current targeted state matches a known operation prefix and the untouched semantic digests still match. The implementation reverses completed operations through native APIs, recompiles, and verifies exact before-state plus untouched digests. Only verified restoration reports `rolled_back`. Unexpected outside-scope change or unknown object/pin state reports `partial_scope_requires_owner`, sets the owner-decision flag, and does not attempt uncontrolled restoration. The package backup is never automatically loaded or copied back.

Complete semantic comparison records are written to `semantic-comparisons.json`. The immediate response returns up to 64 scope summaries with an explicit truncation flag and the complete report path. `result.json` records the operation outcome. Artifact-write failures remain explicit.

Responses distinguish preview generated, Apply completed in memory, compilation attempted/completed/success, retained in-memory changes, rollback attempted/verified, save, independent reload, and runtime behavior. This path always reports `saved:false`; it supplies no general save or reload operation.
